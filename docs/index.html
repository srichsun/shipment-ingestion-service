Shipment Ingestion Service出貨事件接收服務

A lightweight FastAPI service that ingests shipment events published by a warehouse system — it authenticates the caller, validates the payload, enforces a business rule, and forwards the clean event downstream for reporting and analytics. 一個小型的 FastAPI 服務。倉庫把貨出掉後會發出一筆「出貨事件」,這個服務負責接住它:先確認來源身分,再檢查資料對不對,套用一條商業規則,最後把乾淨的事件轉給下游做報表與分析。

The flow流程

One entry point, five steps一個進入點,五個步驟

POST /v1/shipments is the single entry point. Every request flows through the same pipeline: 只有一個進入點:POST /v1/shipments。每一筆請求都照順序走過這幾關:

  1. Authenticate the caller via an X-API-Key header.確認身分:檢查 X-API-Key 這個 header。
  2. Validate the payload structurally — types, enums, field constraints.檢查資料:型別、選項、欄位規則對不對。
  3. Apply business rules — a shipped event must carry a tracking number.套商業規則:狀態是 shipped 就一定要有追蹤號。
  4. Forward the validated event downstream (mocked with a log line).往下游送:把驗過的事件轉出去(這裡用一行 log 代替真的呼叫)。
  5. Acknowledge with 202 Accepted and a correlation_id for tracing.回覆:回 202 Accepted,附一個 correlation_id 方便之後追。

Design decisions設計取捨

Why it's built this way為什麼這樣設計

Structural vs business validation結構問題 vs 商業問題

Structural checks (types, the status/carrier enums, quantity_shipped > 0, non-empty required strings) are enforced by Pydantic. The cross-field business rule — a shipped event must have a tracking number — lives separately in the endpoint. Both return 422 (well-formed but not processable in this state) and are told apart by the code, not the status: a 400 would wrongly suggest a malformed request. They stay in separate layers because they change for different reasons — structural rules follow the data format, business rules follow the business process — so a new business rule never disturbs the schema. Neither ever leaks out as an unexpected 500. 結構的檢查(型別、status/carrier 選項、quantity_shipped > 0、非空的必填欄位)交給 Pydantic。而「shipped 一定要有追蹤號」這種要看好幾個欄位、跟業務有關的規則,我放在 endpoint 自己處理。兩種都回 422(資料格式沒問題,只是這個狀態不能處理),靠 code 分辨、不靠狀態碼——因為回 400 會讓對方誤以為是格式壞掉。它們分在不同層,因為改的原因不一樣:結構跟著資料長相走,商業跟著業務規定走,加新商業規則不會動到資料結構。兩種也都不會不小心變成 500。

One error envelope錯誤都長同一個樣子

The API is consumed by machines, so every error returns the same shape — {"error": {"code", "message"}} (plus details for validation) — with a stable, machine-readable code. Callers write one error handler and branch on code rather than brittle string matching. FastAPI's default 422 is reshaped into this envelope so 401 / 422 stay consistent. 這個 API 是給程式打的,不是給人看的。所以每種錯誤都回一樣的結構——{"error": {"code", "message"}}(驗證錯的話再多一個 details),而且有一個固定、機器可讀的 code。這樣對方寫一套錯誤處理、看 code 判斷就好,不用去比對容易壞的字串。FastAPI 預設的 422 我也改成同一個樣子,讓錯誤一致。

Constant-time authentication身分驗證

The API key is read from the API_KEY environment variable and compared with secrets.compare_digest (constant-time, to avoid a timing attack). A missing header and an invalid key both return 401 with the same message, so the response never reveals which part failed. API key 從 API_KEY 環境變數讀,用 secrets.compare_digest 比對(固定時間,避免被 timing attack 猜出來)。沒帶 header 跟帶錯 key 都回一樣的 401、訊息也一樣,不會透露到底是哪邊出錯。

Tolerant Reader for unknown fields多出來的欄位不擋,但會記下來

Unknown fields are accepted rather than rejected, so upstream systems can evolve their schema without breaking ingestion. Accepted extras are logged as a schema-drift signal instead of being silently dropped. 對方多送了我沒定義的欄位時,我選擇收下、不擋掉,這樣上游改自己的格式時不會害我這邊壞掉。但我會把這些欄位寫進 log,當作「格式好像變了」的提醒,而不是默默丟掉。

Acknowledge with 202 + correlation id回覆用 202 + correlation id

Success returns 202 Accepted — the service accepts the event for downstream processing rather than creating a queryable resource — with the fulfillment_id for reconciliation and a generated correlation_id that also appears in the logs, so a single event can be traced end to end. 成功回 202 Accepted,意思是「我收下了、會往下游處理」,而不是「我建了一筆你可以再查的資料」。回覆帶 fulfillment_id 方便對帳,還有一個 correlation_id——這個 id 也會出現在 log 裡,所以一筆事件可以從頭追到尾。

Scope範圍

Assumptions & what's next假設,以及還會做什麼

Assumptions (kept scope tight)假設(把範圍收緊)

  • A single API key via API_KEY; per-client keys are out of scope.只有一把 API key,用 API_KEY 提供;每個客戶一把先不做。
  • A "valid" tracking number means non-empty; carrier-specific formats (UPS 1Z…) were left out.「有效」的追蹤號先當成非空字串;各家貨運商的格式(UPS 1Z…)先不管。
  • Only status = shipped requires a tracking number; the carrier allowlist is fixed.只有 status = shipped 需要追蹤號;貨運商清單固定。
  • shipped_at is accepted as any valid timestamp — not range-checked (past / future), and not required even when status = shipped.shipped_at 只要是合法時間就收——沒檢查是不是未來 / 太久以前,status = shipped 時也沒強制要填。
  • No persistence — the downstream integration is mocked, per the brief.沒有資料庫——往下游送用 mock 代替,這也是題目本來的意思。

What I'd add with more time有時間的話還會做

  • Idempotency. Events are at-least-once, so a fulfillment_id can arrive twice — dedupe with a unique key on it (skip anything already seen) and return the same acknowledgement. A hook already marks where this belongs.冪等。事件是「至少送一次」,同一個 fulfillment_id 可能來兩次——在資料庫上為它設唯一鍵,重複的就跳過、回一樣的結果。程式裡已先留了位置。
  • Real downstream delivery (mocked with a log today): retry on failure, and hold events that still can't be delivered rather than losing them.真的把事件送到下游(現在用 log 模擬):送失敗時自動重試,真的送不出去的先存起來、別弄丟。
  • Move managed data to a database. Carriers and API keys are hard-coded config today. Once they become per-tenant, business-managed, and carry attributes (API url, keys), they're data, not config — they'd move to carriers / api_keys tables.把會變的資料搬進資料庫。現在 carrier、API key 是寫死的固定設定。等它們變成「每個客戶不一樣、業務要在後台自己增減、還帶欄位(像 API 網址、金鑰)」時,就比較像資料而非設定——那時改用 carriers / api_keys 資料表來存。
  • Authenticate before validation. FastAPI validates the body before the handler runs, and the key check lives inside the handler — so structural validation effectively runs before auth. Moving the key check into middleware (which runs before body validation) would authenticate first. A deliberate trade-off, kept simple here.先驗身分、再驗格式。FastAPI 會在進 handler「之前」先驗 body,而驗 key 在 handler 裡——所以格式驗證排在驗身分前面。把驗 key 移到 middleware(它在 body 驗證之前跑)就能先擋身分。這是刻意保持簡單的取捨。
  • Input hardening. Upper bounds on quantity_shipped, the shipped_items array length, and string lengths — plus a request-size limit — to guard against oversized or abusive payloads.輸入加固。給 quantity_shipped、shipped_items 陣列長度、字串長度設上限,再加請求大小限制,擋掉超大或惡意的 payload。
